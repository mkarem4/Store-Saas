## 1. نظرة عامة

منصة **SaaS متعددة المحلات (Multi-tenant)**:

- **Web:** لوحة للأونر، لوحة لصاحب المحل، لوحة للموظف. ✅
- **Mobile App:** للزبون فقط (iOS + Android)، شبه "طلبات": تصفح المحلات، سلة، **Pickup أو Delivery**، دفع بالبطاقة، سجل الطلبات. ✅ 📨
- الأونر هو اللي ينشئ المحلات ويحدد نوعها. **مفيش تسجيل ذاتي للمحلات.** ✅
- **المحل الواحد له نوع نشاط واحد وموقع واحد (بدون فروع، مؤكد 📨)** (D10).
- **اسم المشروع: «يوليو»** 📨
- **السوق:** الولايات المتحدة، العملة **USD** 📨. **الأردن** ورد في ملاحظة الضريبة، فسؤال "هل هو سوق في Phase 1؟" مفتوح (G1).

### M6. التقارير وصافي الربح ✅

```
الإيرادات      = المبيعات (POS + طلبات التطبيق + بيع السيارات + مدفوعات الإيجار)
                 − المرتجعات − الخصومات        (بدون الضريبة المحصّلة)
COGS           = Σ (تكلفة الصنف لحظة البيع × الكمية)  [والسيارات بالتكلفة الإجمالية]
مجمل الربح     = الإيرادات − COGS
المصاريف       = إيجار + رواتب + عمولات + رسوم دفع + باقي المصاريف
صافي الربح     = مجمل الربح − المصاريف
```

## 6. تدفقات وحالات أساسية

### 6.1 حالات الطلب

| النوع | المسار |
|---|---|
| **Pickup** | `pending → accepted → preparing → ready_for_pickup → completed` |
| **Delivery** | `pending → accepted → preparing → out_for_delivery → completed` |
| **استثناءات** | `rejected` (المحل وهو `pending`) • `cancelled` (الزبون وهو `pending`، أو المحل بعد القبول مع سبب) • `expired` (مهلة القبول 10 دقائق) |

| الحالة | حالة الدفع |
|---|---|
| إنشاء الطلب `pending` | `authorized` (مبلغ محجوز على البطاقة) |
| `accepted` | `captured` |
| `rejected` / `expired` / `cancelled` قبل القبول | `voided` |
| `cancelled` بعد القبول | `refunded` |

- كل تغيير حالة يتسجل في `order_status_history` ويبعت Push للزبون.
- فشل الدفع عند الإنشاء = لا يُنشأ الطلب.

### 6.2 أثر الأحداث على المخزون والتقارير

| الحدث | المخزون | التقارير |
|---|---|---|
| توريد بضاعة | + كمية، ويتحدّث متوسط التكلفة | — |
| بيع POS | − كمية | إيراد (بدون الضريبة) + ضريبة محصّلة + COGS (بتكلفة لحظة البيع) + عمولة الموظف (إن وُجدت) |
| قبول طلب تطبيق | حجز (`reserve`) + Capture للدفع | — |
| رفض / إلغاء / انتهاء مهلة | فك الحجز + Void | — |
| اكتمال طلب تطبيق | يتحول الحجز لخصم نهائي | إيراد (بدون ضريبة) + COGS + ضريبة محصّلة + عمولة المنصة 3% + رسوم Stripe (على المحل) + قيد صافي المحل في محفظته |
| مرتجع | + كمية (افتراضياً) + Refund للبطاقة | − إيراد، وعكس COGS والعمولة، وخصم من محفظة المحل |
| تسوية جرد | ± كمية | — |
| تالف | − كمية | خسارة تسوية (لا تدخل COGS) |
| بيع سيارة | الحالة `sold` | إيراد + COGS (التكلفة الإجمالية) + عمولة الموظف البائع |
| استلام سيارة مؤجرة (دفع كامل) | الحالة `rented` | إيراد وقت الدفع، والتأمين خارج الإيراد |
| تسليم السيارة المؤجرة | تعود `available` | رسوم إضافية (إن وُجدت) كإيراد، ورد التأمين |
| اعتماد كشف رواتب | — | مصروف "رواتب" (شامل العمولات) |

**Multi-tenancy مطبّق بقاعدة بيانات مشتركة وعزل على مستوى السجلات.** كل محل هو Tenant من نوع `Business`.

- **اللوحات والصلاحيات:** لوحتا `business` و`staff` تحددان المحل بالـ`slug`. حساب صاحب المحل أو الموظف مرتبط بمحل واحد، و`User::canAccessTenant()` يطابقه مع `business_id`. صلاحيات Spatie Teams مرتبطة بنفس المعرّف. لوحة إدارة المنصة تدير المحلات مركزيًا. المراجع: `app/Providers/Filament/`، `app/Models/User.php`، `app/Http/Middleware/SetPermissionTeam.php`.
- **السجلات:** موارد المحل تعتمد على Global Scope في `BelongsToBusiness`. الـScope يفلتر النماذج اللي تستخدمه حسب `business_id` ويملأ الحقل عند الإنشاء لو كان فارغًا. `BusinessContext` يحدد المحل من السياق الصريح أو Filament أو المستخدم. لو السياق غائب، الـScope يترك الاستعلام بلا فلترة، لذلك مسارات خارج اللوحات تحتاج قيدًا صريحًا أو سياقًا محددًا. المراجع: `app/Filament/Business/BusinessResource.php`، `app/Models/Concerns/BelongsToBusiness.php`، `app/Support/BusinessContext.php`.
- **الـAPI والعمليات المشتركة:** كتالوج الزبون يفلتر حسب المحل، وحساب الزبون يقدر يطلب من محلات مختلفة ويشوف طلباته هو. الإيصالات مقيّدة بمحل المستخدم، والـStripe Webhook يطابق الطلب بمعرّف الـPayment Intent. المراجع: `app/Http/Controllers/Api/V1/ProductController.php`، `app/Http/Controllers/Api/V1/OrderController.php`، `app/Http/Controllers/ReceiptController.php`، `app/Http/Controllers/StripeWebhookController.php`.
- **التغطية الحالية:** اختبارات عزل استعلامات المنتجات والمبيعات والموظفين، وتعبئة `business_id` عند إنشاء منتج أو Variant، وإخفاء منتج محل آخر ورفض فتح رابط تعديله، وملكية عناوين الزبائن. المراجع: `tests/Feature/TenantIsolationTest.php`، `tests/Feature/Panels/BusinessPanelTest.php`، `tests/Feature/ApiV1Test.php`.
- **المتبقي قبل الـPilot:** توسيع اختبارات العزل عبر المحلات لكل موديول. الأولوية لاختبار دخول صاحب المحل والموظف برابط محل آخر، والإيصالات والتصدير، وعمليات الكتابة على سجلات محل آخر، وطلبات الزبائن والمحفظة والسحب. راجع الاستعلامات خارج سياق المحل والاستثناءات من الـGlobal Scope ضمن التحقق.
- **ملكية طلبات الزبائن:** إعادة استخدام مفتاح Idempotency تُرجع الطلب فقط لنفس الزبون والمحل. عرض الطلب وإلغاؤه يقبلان `?business={slug}` مع رقم الطلب، ويُرجعان 409 عند تطابق الرقم في أكثر من محل لحساب الزبون بدون تحديد المحل. اختبارات المسارين في `tests/Feature/ApiV1Test.php`.
- **إعادة طلبات الدفع:** يستخدم Capture وVoid مفتاح Idempotency مستقلًا وثابتًا لكل PaymentIntent. تجربة إعادة المحاولة والتسوية على Stripe Test Mode ما زالت مطلوبة.

**المبالغ:** أعداد صحيحة (سنت) مع `currency_decimals`، والكميات الوزنية `decimal(12,3)`.

## تسجيل المحلات وصلاحيات الموظفين

- تعرض الصفحة الرئيسية `/` نموذج تسجيل صاحب المحل وقائمة أنواع المحلات النشطة من إعدادات الماستر، ومنها العطور والبقالة ومعارض السيارات.
- تعرض صفحة التسجيل معاينة لإيصال البيع وتحديث المخزون، وتستخدم ملف تنسيق مستقلًا عن Vite. يدعم التصميم الشاشات الصغيرة والعربية من اليمين لليسار.
- تشرح الصفحة رحلة المبيعات والطلبات والمخزون والحضور والرواتب والتقارير، وتعرض أمثلة للأدوات حسب نوع المحل ودور الماستر وصاحب المحل والموظف.
- يعرض داشبورد الماستر عدد المحلات غير النشطة مع رابط لقائمتها للمراجعة. يستطيع صاحب المحل تعديل الاسم وبيانات الاتصال والعنوان من إعدادات محله.
- ينشئ التسجيل المحل وحساب صاحبه والأدوار والفئات الافتراضية في معاملة واحدة. يبدأ المحل بحالة غير نشطة، ويفعّله الماستر من `/admin`، ثم يسجل صاحبه الدخول من `/business`.
- يدير الماستر بيانات المحلات وحالتها وأنواعها وعمولة المنصة من لوحة الإدارة.
- يدير صاحب المحل موظفيه من قسم الفريق. بعد منح الموظف حساب دخول، يستطيع المالك إنشاء دور خاص بالمحل وتعيينه وتعديل صلاحياته من إجراء «دور الموظف». يسري تعديل الصلاحيات على كل موظف يحمل الدور، ويحتفظ الموظف بدوره عند إعادة تعيين كلمة المرور.
